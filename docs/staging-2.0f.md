# Ensayo de staging 2.0F

Complementa [staging.md](staging.md); ninguna instrucción aquí despliega el proyecto.

## Servidor web y compatibilidad

Apache debe apuntar `DocumentRoot` a `public/`, permitir las reglas de reescritura del proyecto y ejecutar PHP 8.4 con las extensiones del lock. Nginx debe apuntar `root` a `public/`, resolver solicitudes a `index.php` y enviar PHP solo al socket PHP-FPM previsto. Denegar archivos ocultos y acceso a rutas internas. Verificar que no existan alias o enlaces públicos a respaldos, logs ni cachés. Antes de publicar, probar accesos HTTP a esas rutas y confirmar que son denegados.

En hosting compartido comprobar la versión PHP tanto de CLI como de PHP-FPM, `pdo_mysql`, extensiones, Composer, document root `public/`, TLS, variables protegidas, límites de procesos y capacidad de ejecutar migraciones y cachés. Un plan que obligue a exponer la raíz del proyecto o no permita proteger secretos no es adecuado. `APP_URL` debe ser el origen HTTPS real. Restringir hosts aceptados en el proxy o servidor web al dominio real; si se utiliza `TrustHosts` en Laravel, configurar una lista explícita y probarla con el hostname final.

El caché de base de datos indicado en el ejemplo permite compartir contadores entre procesos que usen la misma base; revisar privilegios, conectividad y capacidad. Para varios nodos todos deben usar el mismo almacén compartido. El límite por IP requiere configurar correctamente solo las IP/CIDR del proxy confiable.

Los tokens Sanctum actualmente no tienen expiración global: logout, revocación y desactivación siguen vigentes. Se recomienda acordar una caducidad inicial de 30 días y un flujo de renovación compatible con operaciones offline antes de activarla; aplicar el cambio explícitamente, comunicar el efecto sobre sesiones y probarlo en staging. Si se habilita expiración, planificar la purga periódica y solo entonces configurar el scheduler necesario. No cambiar silenciosamente sesiones existentes. Establecer rotación y retención de logs, por ejemplo 14 días tras acordar requisitos, con acceso mínimo, cifrado y exclusión de tokens, contraseñas y cuerpos completos.

## Respaldo y restauración MariaDB: ensayo 2.0F

El ensayo `tests/Staging/restore-check.php` usó un respaldo privado existente, tratándolo como potencialmente sensible y sin exportarlo fuera de la máquina. Su SHA-256 fue `1809a9d72360ed2ee434a44f9332bbdf6bf48620d337027e1d2ccdd791f538af`. Se restauró exclusivamente en una base local nueva con sufijo aleatorio, previamente comprobada, y se eliminó al terminar. Resultado: 21 tablas, ocho migraciones, 13 claves foráneas comprobadas, cero huérfanos, cero usuarios, tokens, pedidos y pagos, y siete productos. El respaldo es anterior a la migración de caja; no representa un respaldo actual con las nueve migraciones. La verificación de huérfanos comprueba cada columna referenciada individualmente y no sustituye pruebas específicas de claves foráneas compuestas.

Para un respaldo nuevo, verificar primero host, servidor y base; usar `mariadb-dump`/`mysqldump` con `--single-transaction` para tablas InnoDB y opciones apropiadas para objetos necesarios. Usar un archivo de credenciales protegido o mecanismo del host, nunca contraseñas en argumentos o logs; guardar fuera del árbol web y cifrar según la política. Registrar hash, fecha, versión y destino. El volcado puede contener datos personales, hashes y tokens: no incluirlo en artefactos ni compartirlo.

Para restaurar, seleccionar una instancia y base nuevas, confirmar su identidad efectiva y que el volcado no contiene `USE`, cambios de base u otras sentencias que apunten a otro esquema. Eliminar o adaptar esas sentencias solamente bajo un procedimiento revisado. Restaurar con el cliente MariaDB usando credenciales protegidas y esa base explícita. Comparar tablas, migraciones, conteos, restricciones e integridad contra la evidencia del respaldo; ejecutar lecturas y probar la aplicación. No restaurar sobre la base activa ni usar el archivo antiguo de este ensayo como respaldo actual. Destruir solo la base desechable identificada tras conservar evidencia sin datos sensibles.

## Smoke y comprobación Android

La colección Postman separa lecturas, seguridad, escrituras y casos de idempotencia. Configurar variables locales sin exportar tokens. Usar únicamente cuentas y datos ficticios en una base desechable; la secuencia de reintento requiere crear primero el pedido con los mismos UUID y cuerpo. `tests/Staging/http-smoke.php` rechaza ejecutarse fuera de la copia y SQLite desechables previstas; genera contraseñas aleatorias y no imprime tokens.

Para una comprobación posterior desde Android físico, usar el dominio HTTPS de staging y un certificado confiable, no `localhost` ni una IP privada codificada en producción. Confirmar conectividad y DNS desde el dispositivo, health, login de una cuenta temporal autorizada, catálogo y sincronización de un pedido ficticio, verificando que un reintento no duplique. No instalar ni borrar datos de la aplicación del dispositivo sin autorización. El Android actual no envía `cash_shift_id`: sus pagos no se imputan automáticamente a caja.

Para construir un artefacto, incluir código, `composer.lock`, `public/` y configuración de ejemplo; excluir `.env` reales, `storage/app/private`, respaldos, logs, cachés locales, `android-integration-work`, pruebas y directorios desechables. Generar `vendor` desde el lock en el destino o pipeline confiable. Revisar el contenido antes de empaquetar; no se generó un ZIP en este ensayo.

## Resultado del ensayo y repetición del smoke

Se instaló desde `composer.lock` en una copia nueva sin `vendor`, con `--no-dev --no-scripts --optimize-autoloader` y sin red; luego se ejecutó `package:discover` explícitamente. Pasaron `composer check-platform-reqs --no-dev`, nueve migraciones en SQLite vacía, `config:cache`, `route:cache` y 18 solicitudes HTTP de smoke a loopback. Se generó una clave temporal independiente y tres cuentas ficticias con contraseña aleatoria solo en SQLite desechable. La instalación y el HTTP utilizaron PHP 8.4 de Herd: no se ha demostrado todavía un runtime independiente de Herd. Docker no estaba disponible y el otro PHP instalado es 8.2, incompatible con el requisito de este ensayo.

Para repetir el smoke, crear una copia exclusiva llamada `.staging-2.0f-disposable` con el código, sin `.env`, secretos ni datos; instalar las dependencias del lock, preparar `storage/` y `bootstrap/cache/`, copiar `tests/Staging/http-smoke.php`, y crear un archivo vacío `isolated.sqlite` en esa copia. En el proceso configurar `APP_ENV=staging`, `APP_DEBUG=false`, una `APP_KEY` nueva y secreta, `DB_CONNECTION=sqlite`, `DB_DATABASE` con la ruta absoluta de ese archivo, `DB_URL` vacío, `CACHE_STORE=database`, `SESSION_DRIVER=file` y `QUEUE_CONNECTION=sync`. Desde la copia ejecutar `php artisan package:discover`, `php artisan migrate --force`, `php artisan config:cache`, `php artisan route:cache` y `php tests/Staging/http-smoke.php`. El puerto 18763 de loopback debe estar libre. Solo después de verificar la ruta exacta, eliminar la copia y su base al terminar. No apuntar este procedimiento a desarrollo.

La colección contiene 35 solicitudes, incluyendo las 30 rutas existentes y cinco casos adicionales; sus 35 scripts pasan comprobación sintáctica. Los scripts no se han ejecutado en Postman ni Newman, por lo que aún debe validarse allí su comportamiento con variables temporales y roles correspondientes. El smoke HTTP ejecutado es independiente de Postman.
