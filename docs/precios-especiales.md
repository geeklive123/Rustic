# Productos ocasionales y precios especiales

Un producto ocasional se crea y administra en el catálogo existente, con categoría, precio y estado. Se vende como cualquier otro producto y conserva la compatibilidad del catálogo actual. No hay una tabla ni un precio libre especial para esos productos.

En `/admin/precios-especiales`, un administrador activo autoriza un precio unitario distinto del precio vigente para una línea concreta: UUID del pedido, vendedor o usuario de cocina, producto y cantidad. Debe indicar el motivo y confirmar. La autorización dura una hora, se identifica por un ID y registra el administrador, precio normal al emitirla, precio autorizado y fecha. Una operación administrativa repetida con los mismos datos devuelve la misma autorización; si cambia el contenido o el administrador, responde 409.

El cliente debe incluir `price_authorization_id` en la línea y enviar el precio autorizado en `expected_unit_price_cents`. El servidor comprueba identidad, producto, cantidad, UUID, vigencia, permiso actual del administrador y precio normal vigente. Comprueba también los precios de extras y el total. Una autorización solo se consume al confirmar la transacción completa; si falla el total u otra validación, no queda consumida. Una venta aceptada se puede reintentar con el mismo cuerpo, UUID y `operation_id`: devuelve la venta original sin otro pago, incluso tras el vencimiento o un cambio de catálogo. Una solicitud distinta o de otro usuario no es un replay válido. El precio aplicado y los extras y componentes se guardan como instantáneas de la venta; la auditoría enlaza autorización, pedido y línea.

Las APK actuales no envían este identificador: venden al precio vigente del catálogo y no pueden aplicar un precio excepcional. Se necesita una integración de cliente posterior para obtener y transmitir el ID y conservar el cuerpo de la operación durante los reintentos. No se ha modificado Android. La autorización no altera el catálogo; tampoco se aplica retroactivamente a pedidos ya existentes. Si cambia el precio normal antes de aceptar la venta, se requiere una nueva autorización. Los importes son centavos enteros y los extras se cobran por separado.

## Migraciones y comprobación

Aplicar las migraciones pendientes mediante el procedimiento de despliegue aprobado, previo respaldo. Las migraciones de auditoría deliberadamente rechazan rollback para proteger el historial; recuperar mediante un plan de restauración verificado, no eliminando tablas. No usar `migrate:fresh` en `rustik_pos_dev`.

PHPUnit usa SQLite en memoria según `phpunit.xml`. Para el ensayo MariaDB usar exclusivamente una base local aislada `rustik_pos_concurrency_test`, con credenciales de prueba y configuración no cacheada. Verificar antes que esa base sea desechable y que `SELECT DATABASE()` confirme su nombre. Ejecutar `artisan migrate --env=testing --force` únicamente después de establecer explícitamente `APP_ENV=testing`, `DB_CONNECTION=mysql`, `DB_HOST=127.0.0.1`, `DB_DATABASE=rustik_pos_concurrency_test`, `DB_URL=` y `DB_SOCKET=` en un proceso separado; revisar la conexión efectiva antes de migrar. Después ejecutar `tests/Concurrency/check.php` y `tests/Concurrency/special-price-run.php` con PHP 8.4. El ensayo crea datos ficticios y verifica reintentos simultáneos, un solo pago y rechazo de reutilización. Los scripts rechazan otra base o host; no sustituyen la verificación previa de la migración.
