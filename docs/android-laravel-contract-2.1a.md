# Contrato Android–Laravel: auditoría 2.1A

* Android identifica la venta con `sales.id` (UUID), guarda el instante en milisegundos Unix, importes en centavos enteros y un `orderNumber` local. El servidor necesita UUID de pedido, UUID de operación, dispositivo, IDs de catálogo y el total esperado. El número devuelto por el servidor es independiente del número local y no cambia documentos ya emitidos.
* Android conserva nombres y precios históricos; Laravel identifica productos, extras y opciones por IDs centrales. No se deben inferir IDs de su posición en la lista ni de una instalación anterior. Los extras locales son nombres unidos por coma con precio agregado; solo se puede construir el cuerpo si se identifica cada extra sin ambigüedad y sus precios suman exactamente el importe histórico. Las opciones gratuitas están a nivel del pedido en Android y a nivel de línea en la API, por lo que se replican en cada línea.
* `EFECTIVO` se traduce a `CASH`; `QR SIMULADO` a `QR_SIMULATED` y no representa dinero recibido de un banco. La API admite `UNPAID`, que el flujo actual de cobro Android no crea. No se transmiten el recibido ni el cambio, porque el contrato actual no los acepta.
* La cola debe guardar el cuerpo y claves inmutables antes del primer envío; `201` es creación y `200` repetición idempotente. `409` exige revisión, `401` reautenticación, `403` falta de permiso, `422` validación y errores de red/5xx requieren reintentos controlados. Un número provisional nunca confirma recepción remota.
* Las fechas de Android son epoch en milisegundos; Laravel devuelve UTC ISO 8601. La API no acepta fecha de venta offline, por lo que `created_at` es fecha de recepción, no la fecha histórica local. Pago, sincronización y cocina son estados separados.
* Historias Room v1–v3 contienen datos que no acreditan pertenencia a una cuenta ni IDs centrales: no se deben enviar automáticamente como nuevos pedidos.
* Para instalar una versión Debug y probarla en un emulador, la URL predeterminada es `http://10.0.2.2:8001/api/v1/`. Para un teléfono físico se configura `-PrustikDebugApiUrl=http://<IP-LAN-DE-LA-PC>:8001/api/v1/` al compilar y se usa un servidor alcanzable en esa interfaz. Solo ese host Debug permite HTTP. `-PrustikReleaseApiUrl=https://<dominio>/api/v1/` configura Release; el valor por defecto es un dominio deliberadamente inválido.
* Las opciones Android se copian a cada línea. El cliente solo resuelve nombres únicos, precios idénticos y extras permitidos por el producto; de otro modo deja un conflicto local. Los IDs y el JSON completo quedan congelados antes del primer envío. La cola está asociada al usuario y a la URL del servidor; una cuenta distinta no puede enviarla.
* Si el POST tiene resultado incierto se reenvía el mismo cuerpo y operación, sin registrar otro cobro local. Después de una respuesta válida se consulta `sync-status`; solo se marca `SYNCED` si UUID y número coinciden. Los documentos locales existentes conservan su número provisional.
* Las colas y sesiones quedan vinculadas a la URL del servidor y al identificador de cuenta; una venta anterior sin origen identificable no se envía automáticamente. Si hay un cobro pendiente de una versión anterior, la pantalla de venta advierte y detiene nuevos cobros hasta que se revise. Las ventas antiguas permanecen en Room y el historial del vendedor muestra solo operaciones atribuidas a su cuenta y servidor; el administrador puede consultar el historial local.
* `SYNC_CONFLICT` conserva el cobro y requiere una revisión manual; esta versión no incluye una interfaz para resolverlo. `SYNC_FAILED` permite reintentar manualmente. Si se cierra sesión sin conexión se borra el token local, pero el servidor no puede revocarlo hasta que exista comunicación; corresponde revocarlo mediante el procedimiento administrativo disponible.
* En la verificación del Sprint 2.1A `rustik_pos_dev` tenía cero categorías, productos, extras y opciones activos. La prueba real utilizó exclusivamente SQLite temporal y datos ficticios. Antes de usar la base central hay que preparar y validar explícitamente el catálogo y las cuentas autorizadas; este sprint no creó usuarios reales ni modificó ese catálogo.
