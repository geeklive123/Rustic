# Reportes web diarios

El panel `/reportes` presenta los pedidos creados durante el día de Bolivia (America/La_Paz), usando límites UTC inclusivo/exclusivo. El total vendido es la suma de los pedidos, incluidos los pendientes y QR simulados; no es equivalente al dinero cobrado. Efectivo y QR_STATIC incluyen únicamente pagos con estado `cash_collected` y `qr_verified`, respectivamente. QR_SIMULATED se muestra aparte y no representa dinero cobrado. Pendientes cuenta pedidos `unpaid` y `qr_pending`. Los productos se agrupan por ID y nombre histórico del pedido; las últimas ventas pertenecen al día actual.

## Publicación segura

El panel queda cerrado por defecto. No se ha configurado ni verificado una red confiable en este proyecto; no exponerlo a Internet hasta instalar y verificar una protección real. Una opción es una VPN privada entre el dispositivo del cliente y el servidor, con acceso al servidor web permitido únicamente desde la subred de la VPN mediante firewall. El cliente se conecta a la VPN y abre la URL HTTPS privada `/reportes` sin introducir credenciales en el panel. La VPN debe establecerse y mantenerse para su dispositivo; si eso no es compatible con el cliente, acordar otra red privada confiable antes de habilitar el acceso.

1. Configurar la VPN, TLS y el firewall para denegar acceso a la aplicación desde redes ajenas; proteger también el origen para que no pueda saltarse el firewall. Comprobar desde dentro y desde fuera de la VPN, tanto IPv4 como IPv6. Una red compartida con usuarios no autorizados no es confiable.
2. Configurar `REPORTS_ALLOWED_NETWORKS` con IP o CIDR específicos de los clientes de confianza, separados por comas, por ejemplo `10.20.0.0/24`. Vacío deniega todo; `/0` se rechaza. Este filtro es defensa adicional, no sustituye firewall ni VPN.
3. El filtro utiliza exclusivamente `REMOTE_ADDR` y nunca cabeceras `X-Forwarded-For`. El servidor web debe pasar la IP real del cliente como conexión directa. No permitir la IP de un proxy compartido ni localhost cuando conexiones externas puedan llegar a través de él: eso permitiría a todos sus clientes pasar el filtro. Si se usa un proxy, instalar la restricción de red en el proxy y configurar una arquitectura que preserve de forma verificable la identidad de red; de otro modo mantener cerrado el panel.
4. Instalar el panel en una instancia independiente para no cambiar las credenciales ni los permisos de escritura del POS. Conectar esa instancia a la base de datos existente del POS usando un usuario de base de datos exclusivo con `SELECT` únicamente sobre `orders`, `payments` y `order_items`, con acceso de red restringido. No ejecutar migraciones ni usar `composer run setup` (incluye migraciones). El panel usa esas tablas directamente; no modifica el backend original.
5. En producción usar `APP_DEBUG=false`, una clave de aplicación propia y configuración segura del servidor. Aplicar los cambios de configuración con `php artisan config:clear` o reconstruir la caché de configuración según el procedimiento del servidor. Validar que `/reportes` responda 403 fuera de la red autorizada, 200 dentro, que los importes coincidan con el POS y que los encabezados indiquen `no-store`.

No se guardan datos del reporte en caché HTTP y la ruta no inicia sesión. La fecha del reporte corresponde a la creación del pedido, incluso si su pago se verificó posteriormente. Para ejecutar las pruebas específicas, usar PHP compatible con Laravel 13 y PHPUnit: `php artisan test --filter=DailyWebReportTest`. Las pruebas crean un esquema SQLite mínimo en memoria sin ejecutar migraciones.


## Historial y detalle: despliegue aislado

El historial pagina 25 pedidos en orden descendente por fecha de creación e ID. La búsqueda exacta por número afecta únicamente a la lista y se combina con el período; los indicadores siguen reflejando todo el período. El detalle utiliza precios, subtotales y nombres guardados en la venta. Las observaciones libres de pedido y producto se omiten porque pueden contener datos personales.

Para desplegar esta mejora, respaldar por separado en el servidor los archivos existentes `app/Http/Controllers/DailyReportController.php` y `resources/views/reports/daily.blade.php`, y copiar únicamente esas dos versiones verificadas. No copiar `routes/web.php`: conserva ajustes propios de SiteGround. No copiar `.env`, configuración, migraciones ni el resto de la aplicación. El usuario de base de datos de reportes necesita SELECT sobre `orders`, `payments`, `order_items`, `order_item_extras`, `order_item_options` y `users` (para el nombre del vendedor); no necesita permisos de escritura. Verificar previamente que el esquema de producción corresponda a las columnas usadas.

Si existe caché de vistas, limpiarla con el procedimiento habitual del servidor, sin regenerar rutas ni cambiar su configuración. Comprobar en HTTPS el resumen existente, un rango antiguo, búsqueda, segunda página, apertura y cierre del detalle, importes históricos y privacidad. Ante cualquier problema, restaurar los dos archivos respaldados y limpiar la caché de vistas si corresponde. No ejecutar migraciones, ni `composer run setup`, ni modificar pagos o Cocina. Las pruebas locales se ejecutan con PHP 8.4 y SQLite en memoria: `php artisan test` y `php vendor/bin/pint --test`.
